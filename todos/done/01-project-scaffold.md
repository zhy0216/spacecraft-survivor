# 01 · 项目脚手架与游戏主循环

- 优先级:P0
- 依赖:无
- GDD 参考:§13 技术方案、§16 风险(性能压测从 M0 开始)

## 背景

技术底座:TypeScript + PixiJS(WebGL)。性能预算(1000 敌 + 500 弹 @60fps)是 GDD 明确要求从第一天就压测的红线,不留到后期。

## 任务

- [x] TypeScript + PixiJS 项目初始化(建议 Vite),`npm run dev` 可跑出画面
- [x] 固定时步 60Hz 逻辑更新 + 渲染插值(逻辑与渲染帧解耦)
- [x] 实体对象池:敌人 / 子弹 / 掉落物全部池化,运行期零 GC 抖动为目标
      —— 敌/弹已池化;掉落物本体属 10 号 issue,`Pool<T>` 是泛型,届时直接复用
- [x] 空间哈希碰撞查询(cell 尺寸 = 最大敌半径 × 2)—— 由 `tuning.enemyRadiusMax * 2` 推导
- [x] 大批量渲染:敌人/弹幕用 ParticleContainer 或 instancing
- [x] 种子化 RNG:全局唯一随机源,seed 可指定
- [x] 常驻压测场景(debug 入口):生成 1000 敌 + 500 弹,显示 FPS/实体计数

## 验收标准

- [ ] 压测场景在中端核显达到 60fps —— **待真机人工验收**,见下
- [x] 人为拖慢渲染(如 30fps 上限)时,模拟结果不变(固定时步生效)—— `src/core/loop.test.ts`
- [x] 同一 seed 两次运行,实体轨迹完全一致(确定性)—— `src/sim/world.test.ts`

## 待人工验收(实现已就位,只差真机)

60fps 那条依赖真实 GPU,Node/vitest 环境验不了,也不写 wall-clock 伪断言(跨机必然 flaky)。
验收方式:`npm run dev` 打开页面,右上角面板「性能 / 确定性」里
`敌(存活)`=1000、`弹(存活)`=500 时读 `fps`。存活计数就是为这条补的 ——
没有它无法确认那个 fps 是在满载 1500 实体下测出来的。
